# Developer Guide

This document describes the code, the decisions made so far and why, and
what is left. Protocol rules belong in the UN-RFCs (`rfc/`); this file is
about the implementation and the reasoning around it.

## Principles

1. **The spec is the product.** If the code and an UN-RFC disagree, the
   code is wrong, or the UN-RFC must be changed through the process in
   UN-RFC 0000. Never let behavior drift silently.
2. **Boring, auditable cryptography.** libsodium primitives through
   PyNaCl. No home-made ciphers. Every hash and signature has its own
   domain separator.
3. **Portable first.** The client must run from a USB stick on a machine
   we do not control. Few dependencies, nothing written outside the stick.
4. **Text network.** No binaries, small articles, bounded storage.
5. **Nobody rules alone.** Group owners, node operators and readers each
   control their own part (UN-RFC 0001 section 4).

## Getting Started

```bash
python -m venv .venv && . .venv/bin/activate
pip install -e ".[dev]"
pytest
```

For a local network without Tor:

```bash
unseenet-node --no-tor --data /tmp/a --listen 127.0.0.1:1119
export UNSEENET_PASSPHRASE=test UNSEENET_INSECURE_FAST_KDF=1   # dev only!
unseenet --vault /tmp/me.vault id-new me
unseenet --vault /tmp/me.vault node-add 127.0.0.1:1119
```

A node config file (TOML):

```toml
[node]
name = "mynode"
min_pow = 18
retention_days = 90
new_groups = "accept"          # accept | trusted | manual

[[peer]]
name = "friend"
address = "abcdef...xyz.onion:119"
groups = "dk.*,comp.*"
key = "ed25519:..."            # the friend's node key (UN-RFC 0016)
```

The documentation is built with `tools/build_docs.sh` (`pip install
mkdocs-material`). The screenshots of the client in
[Using the client](client.md) are made by `tools/docs_screenshots.py`: it
starts a node on your machine without Tor, fills it with made-up people,
groups and posts, drives `unseenet-tui` headless and writes
`docs/img/client-*.svg`. Run it again when the client's look changes, and
commit the files.

The recordings on the front page are made the same way, from the same
made-up content:

- `tools/docs_recording.py` runs the real client in a pseudo-terminal,
  types into it and saves `docs/img/demo.cast`, which the bundled
  [asciinema player](https://github.com/asciinema/asciinema-player) plays
  (`pip install pexpect`; `--gif docs/img/demo.gif` also renders the GIF for
  the README, with [agg](https://github.com/asciinema/agg)).
- `tools/image/record.py IMAGE` boots a bootable image in QEMU, goes through
  the menu and makes a vault, and writes `docs/img/boot.webm` and
  `boot-poster.png` (needs QEMU and ffmpeg; KVM is faster but not needed).

Make them again when the client or the boot menu changes noticeably.

## Design Decisions (so far)

Each decision lists where it is specified and the reasoning. Changing one
means writing a new UN-RFC.

### Python

The maintainer is most productive in Python. The workload is I/O-bound
(Tor latency dominates), so asyncio is more than fast enough. The only
CPU-heavy part, postage, is deliberately expensive anyway.

### Tor via the control port, not stem

`stem` no longer builds on current Python versions. We need four control
commands (AUTHENTICATE, GETINFO, ADD_ONION, and bootstrap status), so
`core/tor.py` speaks the control protocol directly. Bonus: one fewer
dependency, and `ADD_ONION` lets us keep the onion key in our own
encrypted file instead of in Tor's directory (UN-RFC 0007 §3).

Arti (Tor in Rust) could later be embedded for a single-binary build.

### NNTP as the wire protocol (UN-RFC 0005)

Decades of newsreaders, tools and understanding come for free. We use a
strict profile and add capabilities rather than inventing a protocol.
Tor replaces TLS.

### Signed articles, content-derived Message-IDs (UN-RFC 0002)

Usenet's worst problems were forgery: forged posts, forged cancels,
forged newgroups. Signing everything and deriving the Message-ID from the
signed content removes that whole class of problems, and makes duplicate
suppression trustworthy.

### No Path header (UN-RFC 0002 §2.4, 0005 §5.4)

Path recorded every server an article passed through, which tells an
observer where it entered the network. History of Message-IDs is enough
to prevent loops. Readers get a synthetic `Path: not-for-mail` for
compatibility.

### Group IDs include the owner fingerprint (UN-RFC 0004 §1)

There is no registry to prevent two `dk.snak` groups. Instead of fighting
that, the owner's fingerprint is part of the name. The UI shows a short
form and warns about look-alikes.

### Four group types chosen by the owner (UN-RFC 0004 §2)

"Like old Usenet" (open), moderated groups (as Usenet had), channels
(announcements), and closed groups. This covers both public discussion
and private circles on the same network.

### Closed groups: epochs and member keys (UN-RFC 0004 §6)

- Content is encrypted with a key derived from a per-epoch group secret.
- Nodes must be able to reject posts from non-members **without being
  able to read anything**. Solution: a *member key* derived from the same
  secret. Only holders of the secret can produce `Member-Signature`, and
  nodes can verify it with the public member key.
- Removing a member starts a new epoch. A removed member keeps what they
  already received — this is unavoidable and documented.
- MLS (RFC 9420) would add forward secrecy but is far more complex. It is
  a candidate for a later revision.

### Postage instead of accounts (UN-RFC 0006)

Anonymous identities are free, so we make posting cost a little CPU.
SHA-256 is simple and good enough to start; the header names the
algorithm so a memory-hard one (Argon2id) can be added.

### Data at rest (UN-RFC 0007)

- Client: one vault file, Argon2id + XSalsa20-Poly1305, kept decrypted
  only in memory, saved atomically.
- Node: LUKS for the disk; onion key encrypted and handed to Tor over the
  control port; closed groups only ever stored as ciphertext.
- Known limit: Python cannot reliably wipe secrets from memory. For strong
  adversaries, recommend running from Tails.

### Text only, 64 KiB

Keeps storage bounded, nodes cheap, and operators away from the legal
problems binary groups brought to Usenet.

## Open Questions

These are not decided. Discussion welcome — ideally as Draft UN-RFCs.

1. **Co-owners** for groups. (Transferring ownership is
   [UN-RFC 0015](spec/un-rfc-0015.md).)
2. **Hiding the reading pattern** from the node (cover traffic, reading
   from several nodes).
3. **Author-Key visibility** in closed groups. Could be hidden by signing
   only with the member key, at the cost of in-group accountability.
4. **Post-quantum** signatures and key exchange.
5. **Abuse handling for node operators** — a clear, documented way to
   drop groups and peers, and what to tell operators about their
   responsibilities.

Settled since this list was first written: chat and low latency
([UN-RFC 0008](spec/un-rfc-0008.md)), the moderation queue and private
messages ([UN-RFC 0009](spec/un-rfc-0009.md)), node discovery
([UN-RFC 0010](spec/un-rfc-0010.md)), ownership transfer
([UN-RFC 0015](spec/un-rfc-0015.md)), authority over group names
([UN-RFC 0018](spec/un-rfc-0018.md)) and names for identities
([UN-RFC 0019](spec/un-rfc-0019.md)).

## Code Status

Working:

- Full article lifecycle: build, sign, postage, Message-ID, validate.
- Manifests, all four group types, approvals, cancels.
- Closed groups end to end, including invitations via `key-grant`.
- Node acceptance pipeline and ONNTP reader/peering commands.
- Push replication to peers (tested with two nodes over local TCP).
- Own Tor process, onion service, SOCKS connections (not yet covered by
  automated tests, as CI has no Tor).
- Encrypted client vault, a command-line client and a TUI client.
- Tested for real: two nodes in Proxmox LXCs peering over Tor onion
  services; an article posted on one is readable on the other about a
  minute later (most of it the deliberate random forwarding delay).

Missing / rough:

- Feeds are not pipelined; one CHECK at a time.
- The command-line client (`cli.py`) predates `client/session.py` and
  should be moved onto it.
- Argon2id "moderate" needs ~256 MiB RAM while unlocking; fine on a PC,
  worth tuning for small nodes.
- Portable builds are not code-signed (Windows SmartScreen, macOS
  Gatekeeper warn on first start).

## Versioning

There are three independent version numbers. Keeping them apart means the
software can evolve quickly while the network stays compatible.

| What | Where | Rules |
|------|-------|-------|
| **Software** | `unseenet.__version__`, tags `vX.Y.Z` | Semantic versioning (below) |
| **Protocol** | `PROTOCOL_VERSION`, the `Unseenet-Version` header | Changes only through a new UN-RFC (UN-RFC 0000) |
| **File formats** | magic bytes (`UNSVAULT1`, `UNSSIDE1`) and `"v"` fields | A new format gets a new magic or `v`; old files must still open |

### Software versions

[Semantic versioning](https://semver.org/): `MAJOR.MINOR.PATCH`.

- **Before 1.0** (now): anything may change. `MINOR` is raised for new
  features *and* for breaking changes; `PATCH` for fixes only. Every
  release is marked as a pre-release on GitHub.
- **From 1.0**: `MAJOR` for breaking changes (command line, `node.toml`,
  vault format, dropping a protocol version), `MINOR` for new features,
  `PATCH` for fixes.

What counts as breaking: anything that makes an existing `node.toml`,
vault or script stop working, or that stops a node from talking to nodes
running the previous `MINOR` release.

**Compatibility promise:** a release always interoperates with nodes and
clients from the previous `MINOR` release, so a network can be upgraded
one node at a time.

### Making a release

1. Move the entries under `## [Unreleased]` in `CHANGELOG.md` to a new
   `## [X.Y.Z] - YYYY-MM-DD` section, and add the compare link at the bottom.
2. Set `__version__ = "X.Y.Z"` in `src/unseenet/__init__.py`.
3. Commit, then tag and push:
   ```bash
   git tag -a vX.Y.Z -m "Unseenet X.Y.Z" && git push origin vX.Y.Z
   ```
4. `.github/workflows/release.yml` checks that the tag, `__version__` and
   the changelog agree, runs the tests, builds, publishes to PyPI with
   trusted publishing (no API tokens stored anywhere) and creates the
   GitHub release with the changelog section as notes.
5. `.github/workflows/portable.yml` builds the portable zips on Linux,
   Windows and macOS (Apple silicon and Intel), unpacks and self-tests each
   one, combines the USB zip, and attaches them with `SHA256SUMS.txt` to the
   release.
6. `.github/workflows/announce.yml` posts the release notes to
   `unseenet.announce` on Unseenet itself, over Tor, once the release
   workflow has succeeded.

### Release branches and fixes

`main` is where the next minor version is developed. A released minor
version gets a branch only when it needs a fix:

1. Fix it on `main` first, with its test, as usual.
2. If `release/X.Y` does not exist yet, create it from the release tag:
   `git switch -c release/X.Y vX.Y.0 && git push origin release/X.Y`.
3. Carry the fix over with `git cherry-pick -x <commit>` on a branch off
   `release/X.Y`, open a pull request against `release/X.Y`, and let the
   tests run.
4. On `release/X.Y`, move the fix's changelog line into a new
   `## [X.Y.Z]` section, set `__version__`, and tag `vX.Y.Z` there. The
   release workflow builds from the tag, whatever branch it is on.
5. Add the same `## [X.Y.Z]` section to `CHANGELOG.md` on `main`, so the
   history is complete there too.

A release branch takes only fixes: no new features, no protocol changes.
It is supported until the next minor release (see
[SECURITY.md](../SECURITY.md#supported-versions)). Development builds are
made from `main` only.

### Test releases and development builds

An **alpha** (or beta, or release candidate) is a release for testing,
with a PEP 440 version: `0.2.1a1`, `0.2.1b1`, `0.2.1rc1`. Make it like a
release, but leave the changelog entries under `## [Unreleased]` - they
become its notes:

```bash
# __version__ = "0.2.1a1" in src/unseenet/__init__.py, commit, then:
git tag -a v0.2.1a1 -m "Unseenet 0.2.1a1" && git push origin v0.2.1a1
```

It is published to PyPI and GitHub as a pre-release (pip takes it only
with `--pre`) and announced as a test release.

**Development builds** need nothing: every push to `main` that changes the
software runs the *portable* workflow, which builds the zips with a
version from `tools/dev_version.py` (`0.2.1.dev3`: three commits after
v0.2.0; written into the build only, never committed) and replaces the
pre-release [`dev`](https://github.com/unseenet/unseenet/releases/tag/dev)
with them. Its notes are the Unreleased changelog and the commits since
the last tag. They are not published to PyPI.

The portable builds can also be made without a release: run the
*portable* workflow by hand (Actions, "Run workflow") and download the zips
from the run's artifacts. Before a release, check `tools/tor-version.txt`
against `python tools/build_portable.py --check-tor` (the *tor-update*
workflow opens an issue when Tor has a newer stable release).

Between releases, every change that users or node operators would notice
gets a line under `## [Unreleased]`.

## Issues, Labels and the Changelog

Every change that users or node operators would notice has an issue, so
the release notes can say what changed and link to the discussion:

1. Open an issue (or use the existing one). The forms add a type label
   (`bug`, `enhancement`, `documentation`), an area label and `triage`.
2. Remove `triage` once you have looked at it; fix the labels if needed.
3. Mention the issue in the commit: `Fixes #12` closes it when the commit
   reaches `main`, `Refs #12` only links it.
4. End the changelog line with the issue number: `- ... (#12)`. The release
   notes are made from `CHANGELOG.md`, so the number becomes a link there.

| Label | Meaning |
|-------|---------|
| `bug`, `enhancement`, `documentation`, `question` | What kind of issue it is |
| `area: client`, `area: node`, `area: protocol`, `area: portable`, `area: bootable`, `area: docker`, `area: docs`, `area: infra` | Which part it is about |
| `security` | Affects the safety, privacy or anonymity of users (report weaknesses privately, see `SECURITY.md`) |
| `breaking` | Breaks compatibility: protocol, file formats, command line or `node.toml` |
| `triage` | New, not looked at yet |
| `good first issue`, `help wanted` | For contributors |
| `node-request`, `accepted` | Requests to join the known-node list (UN-RFC 0010) |
| `hierarchy-request` | Requests for a hierarchy in the project's root list (UN-RFC 0018) |

### Milestones

What is planned for which release is kept as
[milestones](https://github.com/unseenet/unseenet/milestones) on GitHub,
so anyone can see what comes next and how far it is:

- one milestone per release (`0.3.0`, `0.4.0`, ...), with a line saying
  what the release is about, and every issue and the release pull request
  in it;
- **Later** for what is wanted but not planned for a release yet - a good
  place to look for something to work on.

Give an issue a milestone when it is planned; a milestone is closed when
its release is out. Issues without one are not planned yet.

## Coding Conventions

- Python 3.11+, type hints, `from __future__ import annotations`.
- Reference the UN-RFC section in docstrings where code implements one.
- Every protocol rule gets a test. Security-relevant rejections get a
  negative test (see `tests/test_protocol.py`).
- Commit messages: imperative mood; mention the UN-RFC if relevant.
